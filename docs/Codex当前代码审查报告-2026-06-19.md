## 总体结论

当前版本比 2026-06-18 的旧审查基线有明显推进：DevJob ownership、Review 幂等、需求库状态同步、桌面端 Runner 接入、评审详情页、PyJWT 迁移、Runner 状态机约束等关键工作已经落地。自动化检查整体通过，可以继续作为本地开发基线。

但当前代码仍不建议直接进入真实用户开放测试。核心问题集中在两类：

1. **真实 Runner 可信链路仍未闭合**：状态机只约束了 `events.status`，但 artifact 写入和 Review 生成仍没有绑定到“持有 lease 且已真实完成的 Runner”。这会导致“未真实执行也能生成评审报告”的信任缺口。
2. **桌面端长任务稳定性仍不足**：Tauri 执行路径缺少 timeout/cancel，CLI 卡死时前端会持续心跳、任务一直 running；同时长中文输出仍可能触发 Rust 字符串切片 panic。

最终判断：

- 可以继续本地开发：是。
- 可以作为 Claude/Codex 互审基线：是。
- 可以给少量内部受控账号跑真实 Runner：谨慎，仅限非敏感仓库和短任务。
- 可以开放给真实用户使用：暂不建议。
- 下一阶段最高优先级：补齐 Runner lease/artifact/review 的可信执行链，并给桌面端 Runner 加 timeout/cancel。

### 关键压力点

- 后端只校验 job belongs to current user，但 artifacts 没有校验 lease、runnerId、job 状态、artifact kind 和终态前置条件。
- Review 生成没有要求 job 必须是 `completed/completed_with_warnings/failed/blocked` 之类终态。
- 桌面端 Tauri 进程等待没有 timeout；前端 heartbeat 会持续把 job 保持为 running。
- 需求库状态展示依赖最新 review/job 的可信度，一旦 Review 可提前生成，需求库就会被错误推进到“已评审”。

## P3：设计决策判断

“后端管状态，桌面端管执行”是正确方向，应该保留。它避免服务器直接执行 Codex/Claude Code，也符合用户本机 CLI 授权模型。

当前问题不是方向错，而是信任链还差最后一段工程化约束。最小合理改动不是重写 Runner，而是把 `lease -> event -> artifact -> review` 变成单一状态机：

- 只有持有有效 lease 的 runner 才能写 event/artifact。
- artifact 必须来自合法状态和合法 engine。
- review 必须基于终态 job 和可解释证据生成。
- 桌面端必须能 timeout/cancel，不允许无限 running。

10x 规模下最先失败的是 Runner 与 Review 的可信度：任务越多，越容易出现僵尸任务、伪完成、报告重复和用户看不懂产物来源。

## 主要发现

### R1 / P0：Review 仍可基于未完成或不可信 artifact 生成，Runner 可信链未闭合

位置：

- `backend/app/modules/runner/router.py:354-381`
- `backend/app/modules/runner/router.py:385-402`
- `backend/app/modules/review/router.py:153-171`
- `backend/tests/test_review.py:202-224`

问题：

`append_dev_job_event` 已经有状态机校验，这是进步；但 `append_dev_job_artifact` 只校验 job ownership，然后无条件接受任意 artifact。`create_review_record` 随后直接读取 events/artifacts 生成报告，不检查 job 是否终态、不检查 artifact 是否来自有效 lease、不检查是否存在真实 run-log。

当前测试还显式接受“没有 artifacts 的 queued job 也能创建 review”，见 `test_review_report_marks_evidence_gap_without_artifacts`。这会让“证据不足报告”成为合法 workflow 产物，需求库只要看到 review 就会显示 `reviewed`。

影响：

- 用户可能在未真实完成开发时看到评审报告。
- 需求库会基于 review 推进状态，造成“已评审/有分数”的误导。
- 恶意或误操作 API 调用可以伪造自己的开发证据，自动评审可信度下降。

建议：

- 给 `DevJobEventCreate` / `DevJobArtifactCreate` 增加 `runnerId`，并要求匹配未过期 lease。
- artifact kind 建立白名单：`run-log`、`diff-summary`、`test-report`、`security-scan`、`secret-scan`、`runner-unavailable`。
- `POST /reviews` 和 `regenerate` 要求 job 已进入终态；如果 job 非终态，只允许返回 `409` 或创建 `blocked/evidence_gap` 类型的内部诊断，不应作为正式 ReviewReport。
- `completed` 或 `completed_with_warnings` 至少要求存在 `run-log.exitCode == 0` 或明确 `runner-unavailable/failed` 证据。
- 增加回归测试：queued job 不能生成正式 review；无 lease 不能写 artifact；lease 过期不能写 event/artifact；非终态不能进入需求库 `reviewed`。

### R2 / P1：桌面端 Runner 没有 timeout/cancel，CLI 卡死会导致任务长期 running

位置：

- `src/services/localRunnerService.ts:57-73`
- `src/services/localRunnerService.ts:123-132`
- `src-tauri/src/lib.rs:326-328`

问题：

前端在执行期间每 15 秒上报 heartbeat，Tauri 端用 `wait_with_output()` 等 CLI 结束。这里没有超时、取消、kill 或用户中断路径。如果 Codex/Claude Code 卡住，前端 heartbeat 会持续刷新事件，后端 stale 检测不会触发，任务会一直显示 running。

影响：

- 用户会看到进度长期停在某个百分比。
- “程序无响应”或“真实开发一直不结束”的体验会反复出现。
- 任务无法可靠进入 failed/blocked 终态，后续评审和需求库状态也无法稳定推进。

建议：

- 在 Rust 端实现进程超时，默认读取前端/后端配置，例如 30 分钟。
- 增加 `cancel_agent_runner(jobId)` Tauri 命令，记录 child pid，并允许 UI 手动取消。
- 超时或取消时写入 `desktop.runner.timeout` / `desktop.runner.cancelled` 事件，并设置 job `blocked` 或 `failed`。
- heartbeat 不应无限增长；达到超时窗口前应提示“仍在运行，可取消”。

### R3 / P1：Rust `trim_output` 按字节切字符串，长中文输出可能 panic

位置：

- `src-tauri/src/lib.rs:205-214`
- `src-tauri/src/lib.rs:336-337`

问题：

`trim_output` 使用 `&value[..LIMIT]` 截断字符串。Rust 字符串切片必须落在 UTF-8 字符边界；当 CLI 输出大量中文、emoji 或其他多字节字符，并且第 40000 字节落在字符中间时，会 panic。

影响：

- Runner 已经执行完成，但桌面进程在整理 stdout/stderr 时崩溃或返回异常。
- 用户看到任务卡住或本地 Runner 无响应。
- 这类问题会在中文项目、中文日志和中文测试输出里更容易触发。

建议：

- 改成 `char_indices` 安全截断，或按 `chars().take(...)` 截断。
- 增加 Rust 单测：输入 40000 字节附近的中文字符串不 panic，且保留 truncation 提示。

### R4 / P1：后端 Docker 镜像没有使用 `uv.lock`，依赖“已锁定”没有进入部署路径

位置：

- `backend/Dockerfile:8-14`
- `backend/pyproject.toml:6-21`
- `backend/uv.lock`

问题：

Claude 这版已经提交 `backend/uv.lock`，本地 `uv lock --check` 通过。但 Dockerfile 仍然只复制 `pyproject.toml` 并执行 `pip install "."`，不会使用 `uv.lock`。生产镜像构建仍会根据 `pyproject.toml` 的 `>=` 范围解析最新依赖。

影响：

- 服务器部署和本地测试可能使用不同依赖版本。
- PyJWT、FastAPI、SQLAlchemy、cryptography 等核心依赖未来升级时，镜像构建可能出现不可复现行为。
- 安全修复“锁依赖”的收益没有覆盖 Docker 部署。

建议：

- Dockerfile 改为复制 `uv.lock`，安装 `uv` 后执行 `uv sync --frozen --no-dev`，或导出 hash-pinned requirements 再用 pip 安装。
- CI 增加 `docker build backend` 验证。

### R5 / P2：读接口会修改 job 状态，轮询本身有副作用

位置：

- `backend/app/modules/runner/router.py:88-117`
- `backend/app/modules/runner/router.py:228-236`
- `backend/app/modules/runner/router.py:414-421`

问题：

`GET /dev-jobs/{id}` 和 `GET /dev-jobs/{id}/events` 会调用 `mark_stale_desktop_job_if_needed`。这个函数在读请求里可能把任务写成 `blocked` 并提交 DB。

影响：

- 普通页面刷新或报告档案轮询可能改变任务状态。
- 如果真实 Runner 在长时间构建但事件上报延迟，读取接口可能抢先把任务标为 blocked。
- 读写混在一起会让故障复现更困难。

建议：

- 把 stale 检测移到后台 worker 或显式维护任务状态的调度器。
- GET 只返回当前状态；若要展示 stale，可返回派生字段 `stale: true`，不要直接改库。

### R6 / P2：Tauri 未配置 CSP/capability，命令桥暴露面偏宽

位置：

- `src-tauri/tauri.conf.json:12-22`
- `src-tauri/src/lib.rs:362-370`

问题：

当前 Tauri 配置没有 `app.security.csp`，也没有 `capabilities` 目录。`invoke_handler` 暴露了 `open_local_path`、`start_agent_runner`、`execute_agent_runner` 等能力。前端目前没有明显 XSS，但桌面端一旦出现渲染层注入，命令桥风险会被放大。

影响：

- 本地文件打开、CLI 执行、工作区创建都属于高权限动作。
- 缺少 CSP 和 capability 会降低桌面端防御纵深。

建议：

- 配置严格 CSP。
- 增加 Tauri capability，只允许当前窗口调用必要命令。
- 逐步废弃旧的 `start_agent_runner` / `build_agent_runner_command`，统一走受控 `execute_agent_runner`。

### R7 / P3：`package.json` 与 `package-lock.json` 根依赖元数据不一致

位置：

- `package.json:14-33`
- `package-lock.json:10-29`

问题：

`package.json` 已经改为精确版本，例如 `@heroui/react: 2.8.10`、`vite: 6.4.3`，但 `package-lock.json` 根节点仍保留旧的 `^` 范围。实际 lock 中的 `node_modules/*` 版本已经是新版本，`npm ci --dry-run` 也通过，所以这不是当前构建阻断问题，但会让依赖审计和代码审查产生歧义。

建议：

- 重新生成并提交一致的 `package-lock.json`。
- 后续依赖升级必须同时包含 `package.json` 与 `package-lock.json`，并记录 `npm ci`/build 结果。

### R8 / P3：`.env.example` 与实际腾讯云邮箱配置目标不一致

位置：

- `backend/.env.example:10`
- `backend/.env.example:22`
